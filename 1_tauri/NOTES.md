# NOTES — config 1 (Tauri)

## Streaming data model (added in rev 2)

- Layout: 4000-bar static preload (`get_initial_bars` / `chart{i}.init.json`)
  → batch indicators over the preload → then 19,400 bars stream in ~50ms
  batches (`start_stream` Tauri events `bar-batch-{chart}` / `stream-done-{chart}`,
  one std::thread per chart; web: `chart{i}.rest.json` fetched once and
  replayed via `setInterval`).
- `src/stream.ts` `IncrementalIndicators` replays the preload through the
  same per-bar update path (identical FP op order), so seeded state is
  bit-identical to batch `computeAllJs` — verified to 1e-9 in vitest for all
  8 charts, both empty-seed and 4000-seed variants.
- `?rate=N` bars/sec; `?rate=0`/absent → 1000; bench mode → 2000 requested.
  Batch size = ceil(rate × 50ms).

### Stream throughput — honest numbers

`series.update` on a Lightweight-Charts series costs ~0.14ms isolated and
~0.3-0.4ms in context (grows with point count + attached series/primitives).
Per spec every streamed bar gets a `candle.update`, so the single
main-thread update budget (~2500 calls/s) is shared by 8 charts:

- Measured effective rate: ~500-600 bars/s **aggregate** (~60-75/s per chart)
  under memory contention, ~200-250/s per chart idle. Catch-up of 19,400
  bars takes ~65-315s depending on machine load — recorded honestly as
  `stream_rate_bars_per_sec` + `stream_catchup_ms` in the results JSON.
- Optimisations applied: line series update once per batch (per-bar
  indicator *state* is still incremental; the exact `setData` reconcile runs
  at stream end — 6 updates/bar was the original throttle to ~50 bars/s);
  visible window follows a ~500-bar tail during catch-up, `fitContent()` at
  end; profile recomputes once per batch.
- IPC itself is NOT the bottleneck: a 100-bar event batch is ~10KB; Tauri's
  serde JSON event path handles that trivially vs the render/update cost.
- Puppeteer needed `protocolTimeout: 900s` — the renderer main thread stays
  ~100% busy during catch-up and CDP evals starve otherwise.

## TA-Lib choices

- **JS path — `talib-wasm` 3.0.1** (npm, insane-jo). The *official* TA-Lib org
  TypeScript port is **not yet published on npm** (per ta-lib.org/api/typescript —
  source-build only). Of the community WASM ports, `talib-wasm` is the most
  maintained option and is an unmodified emscripten build of the official C
  library (the reference implementation itself).
- **Fallback/hack**: the package's JS wrapper (`wrap-talib-function.js`) has a
  heap-corrupting bug — it calls `Module._free(offset / 8)` on byte pointers,
  which aborts(OOM) on 23k-bar inputs. We bypass the wrapper entirely: load
  `talib-wasm/build/talib.wrapped.min.js` (the raw emscripten module) and call
  `TA_EMA`/`TA_SMA` via `cwrap` with correct malloc/free (see
  `src/indicators.ts`).
- The emscripten bundle also relies on sloppy-mode `this` (reads `this.abort`
  in its ready-promise). Bundled as ESM it's strict and crashes, so we evaluate
  the bundle text inside `new Function` with a fake `module.exports`. Works in
  both Chrome and WebView2. `new Function` needs no CSP `unsafe-eval` issues
  here because tauri.conf sets no CSP.
- **Rust path**: pure-Rust `shared/indicators` reference implementations via
  Tauri commands (preload `compute_indicators` with `count` slicing; a
  `start_stream` thread emits bar batches). A real TA-Lib Rust binding
  (`ta-lib`/`talib` crates) was not integrated — they need the C library
  installed; not trivially available, so documented fallback per spec.
- **Parity**: vitest compares both JS paths against golden JSON generated by
  `cargo run --bin gen_golden` (Rust reference). All 8 charts × all series
  match within 1e-6 after warmup (in practice ~1e-12; TA-Lib EMA uses the same
  SMA-seed convention as the reference). Incremental stream indicators match
  batch output within 1e-9.

## Bench numbers worth knowing (this machine, headless)

- Web indicator compute: ~4ms/chart (median) — TA-Lib WASM + JS.
- Desktop indicator compute: ~96ms/chart — dominated by `invoke` +
  serde_json round-trip of ~234k numbers per series (5 series + bins), not
  the Rust math itself. If this matters, return typed arrays / a packed
  binary payload instead of JSON.
- Desktop startup 13.7s vs web 2.3s: desktop number includes WebView2
  initialization + all-8-charts render path in a headless-ish window; treat
  the desktop startup figure as approximate.
- 100 updates/sec/chart (800 series.update calls/s across 8 charts) is the
  stress case: ~6-7 fps in headless Chrome, ~2 fps in WebView2. Everything
  else sustains 25-75 fps.
- `performance.memory` is Chromium-only (fine: Chrome + WebView2 are both
  Chromium). `--enable-precise-memory-info` used for the headless run.

## Pain points / environment

- Node 22.11 vs required >=22.12: vite 8 + rolldown warn EBADENGINE but work.
- npm optional-deps bug: `@rolldown/binding-win32-x64-msvc` was missing after
  install → `npm i -D @rolldown/binding-win32-x64-msvc` fixed it.
- TypeScript 7 (`erasableSyntaxOnly`) bans constructor parameter properties
  (`private readonly x` in ctor args) — volprofile.ts uses explicit fields.
- dockview 8 split packages: React components live in `dockview-react`, not
  `dockview` (which now only re-exports dockview-core).
- LWC v5: `chart.addSeries(CandlestickSeries)` API (v4's addCandlestickSeries
  gone); volume profile implemented as `ISeriesPrimitive` with
  `useMediaCoordinateSpace` + `series.priceToCoordinate` — independent scale,
  right-edge anchored, `zOrder:'normal'` (under crosshair).
- `tauri build` needed: non-default `identifier`, and `default-run = "app"`
  in Cargo.toml once a second bin target (`gen_golden`) existed.
- Desktop bench ran headless fine: `app.exe --bench` → `bench_requested`
  command → same `?bench=1` flow inside WebView2, `save_results` writes
  `results/tauri-desktop.json` and injects `artifact_size_mb.exe` (17.4 MB).
- **No shared-crate changes were needed**; nothing was copied locally.
- Unidentified `chart{i}.init.json` / `chart{i}.rest.json` files briefly
  appeared in `public/data/` (likely another agent's process) — removed; the
  config only uses `chart{i}.json`.
